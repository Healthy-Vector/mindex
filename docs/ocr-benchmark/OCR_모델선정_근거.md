# 1. 왜 CER이 아니라 CORE 필드 보존율인가

일반적인 OCR 평가 지표는 CER(문자 오류율)이다. 그러나 **이 프로젝트에서는 부적절하다.**

CER은 다음 두 오류를 **동일한 1점**으로 계산한다.

| 오류 | 실제 영향 |
|---|---|
| 제목 `콘텐츠 이용허락 계약서` 가 깨짐 | 없음 — 판정에 사용되지 않음 |
| `2026년 1월 1일` 이 깨짐 | **R6(기간) 판정 전체가 무효** |

실측에서도 이 왜곡이 확인되었다. Tesseract는 CER 13.86%(정확도 86.1%)로 낮게 나왔으나, 오류가 **제목·장식 문자에 집중**되어 있었고 날짜·금액·지역은 정확히 추출되었다.

```
Tesseract 출력 (제목 부분)
  텐 / [= / 대 / I> / ols / Ql / 락 계약서    ← 제목이 조각남

Tesseract 출력 (본문 부분)
  본 계약에 따른 이용허락 기간은 2026년 1월 1일부터
  2027년 12월 31일까지로 한다.                 ← 정확
```

따라서 **판정에 실제로 사용되는 필드가 보존되는지**를 기준으로 삼았다. 대상 필드는 P3의 「계약서 파싱 필드 및 label 정리」 문서의 CORE Field를 따랐다.

| 검사 필드 | 대응 판정 규칙 |
|---|---|
| content (콘텐츠) | R1 Content Identity |
| territory (지역) | R5 Territory Scope |
| mode (이용형태) | R4 Exploitation Mode |
| exclusivity (독점) | R7 Exclusivity |
| start / end (기간) | R6 License Period |
| amount (금액) | 암호화 대상 (SER-006) |
| sublicense (재허락) | R8 Authority / Rights Chain |

> 대안 표현을 함께 검사한다. 예를 들어 `SVOD` 가 깨져도 같은 줄의 `구독형 주문형 비디오` 가 살아 있으면 정규화로 복원 가능하므로 성공으로 본다.

# 2. 실측 조건

| 항목 | 내용 |
|---|---|
| 시나리오 | KO-N01 (C001 겨울의 신호, 일본 SVOD 독점, 2026.01~2027.12) |
| 원문 | 6개 조항, 한국어, A4 2페이지 |
| 스캔본 생성 | PDF → 200dpi 렌더 → 흑백화 → ±1.2° 회전 → 가우시안 블러 0.6 → 소금·후추 노이즈 0.2% |
| 측정 환경 | MacBook (Apple Silicon), 웜 스타트 (모델 로딩 제외) |

**스캔본이 없어 합성했다.** 원문을 알고 있으므로 정확도를 정량 측정할 수 있다는 이점이 있다.

## ⚠️ 노이즈 조건 정정 (2026-08-19)

위 조건은 **과했다.** 계약서는 법적 문서라 흐릿하게 인쇄되지 않는다. 팩스본·복사본이라도 원본은 깨끗한 인쇄물이며, 블러 0.6 + 소금·후추 0.2% 는 팩스 재전송 3회급 열화에 해당한다.

`01_make_samples.py` 를 현실적 조건으로 수정했다 — **200dpi + 흑백 + ±0.5° 급지 기울임**만 남김.

> **결론은 유지된다.** 더 나쁜 조건에서 PaddleOCR 이 CORE 100% 를 냈으므로, 조건을 완화하면 최소 동일하거나 개선된다. 다만 Tesseract 의 `mode` 실패가 노이즈 때문이었는지 확인하려면 재측정이 필요하다 — 재측정 후에도 실패하면 폰트·자간 문제이므로 판단이 더 확실해진다.

## 실제 계약서에서 더 어려운 것

노이즈보다 실제로 문제가 되는 조건은 따로 있다.

| 조건 | 영향 |
|---|---|
| 도장·직인이 글자 위에 겹침 | 해당 글자 인식 실패 |
| 표(Schedule) 안의 값 | 일반 텍스트 OCR 로 순서가 뒤엉킴 — RB-KO03 |
| 각주·별지 분산 | 조항 분할 시 맥락 유실 |
| 세로쓰기 일본어 계약서 | 별도 처리 필요 |

→ 실물 확보 시 이 조건들로 재측정한다. 흐릿함이 아니라 **구조**가 관건이다.

# 4. 속도 트레이드오프

PaddleOCR이 **23배 느리다.** 그럼에도 채택하는 이유:

| 상황 | 소요 시간 | 판단 |
|---|---|---|
| 시나리오 72건 일괄 처리 (≈144페이지) | 약 35분 | 배치 작업이므로 수용 가능 |
| 실시간 업로드 1건 (2페이지) | 약 28초 | 시연 시 대기 시간 발생 — **주의 필요** |

## 최적화 여지

PaddleOCR은 실행마다 모델 5개를 로드한다.

```
PP-LCNet_x1_0_doc_ori        문서 방향 감지
UVDoc                        휘어짐 보정
PP-LCNet_x1_0_textline_ori   텍스트라인 방향 감지
PP-OCRv5_server_det          텍스트 검출
korean_PP-OCRv5_mobile_rec   한국어 인식
```

앞의 3개는 **스마트폰 촬영본처럼 심하게 뒤틀린 이미지**를 위한 전처리다. 우리 대상(스캔 PDF)에는 과잉이므로 비활성화하면 속도가 크게 개선된다.

```python
PaddleOCR(
    lang="korean",
    use_doc_orientation_classify=False,
    use_doc_unwarping=False,
    use_textline_orientation=False,
)
```

> 시연에서 실시간 업로드를 보여줄 계획이라면 이 최적화가 필요하다. **P3·P5와 협의 필요.**

# 6. 임베딩 모델

**변경 대상이 아니다.** RFP SFR-005에서 `multilingual-e5-large` (1024차원, 로컬 구동)로 확정되어 있다. 본 작업에서는 선택이 아니라 **동작 검증**만 수행한다.

## 구현 시 주의 (P3 전달 사항)

e5 계열은 접두사 규칙이 있다. 누락하면 학습된 벡터 공간과 어긋나 검색 품질이 떨어진다.

```python
# 문서 저장 시
model.encode(f"passage: {chunk}", normalize_embeddings=True)

# 검색 질의 시
model.encode(f"query: {question}", normalize_embeddings=True)
```

`normalize_embeddings=True` + 코사인 거리(`vector_cosine_ops`) 조합을 사용한다.

# 7. 서버 환경 (P1 확인)

| 단계 | 실행 위치 | 메모리 | 비고 |
|---|---|---|---|
| PDF 파싱·OCR | 개발 PC | ~1–2GB | |
| e5-large 추론 | **개발 PC** | **~3GB** | 모델만 2.2GB |
| 벡터 저장·HNSW 검색 | EC2 5432 | 기존 컨테이너 | |

🔴 **EC2(t3.small, RAM 2GB)에서 임베딩·OCR 추론 금지.** DB 두 개가 이미 가동 중이며 여유 메모리가 없다. 실행 시 서버가 정지해 **팀 전원의 작업이 중단**된다.

공용 추론 서버가 필요해지면 `t3.large`(8GB, 약 $0.10/시간) 증설을 검토한다. 현재 규모에서는 불필요하다.

# 8. 남은 확인 사항

- [ ] **EN·JA 샘플 측정** — 현재 KO만 검증됨. 시나리오가 3개 언어이므로 `lang="japan"`·`lang="en"` 결과 확인 필요
- [ ] **Robustness 12건 적용** — RB-KO01~04, RB-JA01~04는 OCR 검증 전용 케이스 (표 구조, 각주, 별지 분산 등)
- [ ] **표(Table) 추출** — RB-KO03이 `Schedule 표` 기반 Multi-Grant 추출을 요구. 일반 텍스트 OCR과 다른 문제이므로 별도 검증 필요
- [ ] **실물 스캔본 재측정** — 합성 데이터의 한계 (§2)
- [ ] **속도 최적화 적용 여부** — 실시간 시연 계획에 따라 결정 (§4)
